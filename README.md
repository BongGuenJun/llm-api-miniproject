# LLM Inquiry Analysis API

사용자의 문의를 Gemini API로 분류·요약하고, Zod로 입력과 출력 구조를 검증하는 TypeScript·NestJS 미니프로젝트입니다.

LLM을 직접 학습하는 프로젝트가 아니라, 외부 LLM API를 서비스 기능으로 연결하고 결과를 평가하는 프로젝트입니다.

## 프로젝트 목적

단순히 프롬프트를 보내고 답변을 출력하는 수준에서 확장해 다음 과정을 구현했습니다.

- HTTP API로 문의 입력받기
- 정해진 분류 기준에 따라 구조화된 결과 생성
- 입력 및 LLM 출력 검증
- 요청 시간 제한과 제한된 재시도
- 고정 평가셋을 사용한 프롬프트 A/B/C 비교
- 실행 결과와 실패 사례 기록

## 기술 스택

- TypeScript, Node.js
- NestJS, Express
- Google Gen AI SDK (`@google/genai`)
- Gemini API
- Zod
- Git, GitHub

개발 환경은 Windows이며, Node.js `v26.13.0`, npm `11.20.0`에서 실행을 확인했습니다.

## 주요 기능

| 기능 | 설명 |
|---|---|
| `GET /health` | 서버 응답 상태 확인 |
| `POST /analyze` | 문의 분류·요약·후속 조치 필요 여부 반환 |
| 입력 검증 | `text`가 공백 제거 후 1~2000자인지 검사 |
| 출력 검증 | JSON 변환 후 필수 필드·타입·허용된 카테고리 검사 |
| 시간 제한 | API 요청 1회당 60초 |
| 재시도 | HTTP 503 발생 시 2초 대기 후 최대 1회 재시도 |
| 평가 | 고정 문의 20개에 대한 정답 여부·소요시간·오류 저장 |

이 API는 문의를 분석합니다. 실제 예약 변경·취소를 수행하거나, 주차 가능 여부 같은 운영 정보를 조회하지는 않습니다.

## 분석 기준

### 카테고리

| 값 | 기준 |
|---|---|
| `예약 변경` | 기존 예약의 날짜·시간 변경 |
| `예약 취소` | 기존 예약 취소 |
| `이용 문의` | 운영 시간·위치·이용 방법 등 정보 질문 |
| `기타` | 위 항목에 해당하지 않거나 의도가 불명확한 입력 |

여러 의도가 포함되면 예약 변경 또는 취소 요청을 우선하도록 프롬프트에 지정했습니다.

### 후속 조치 필요 여부

`requiresAction`은 직원의 예약 처리나 추가 확인이 필요한지를 나타냅니다.

- 예약 변경·취소 요청: `true`
- 단순 정보 문의: `false`
- 담당자 확인·연락을 명시적으로 요청한 불만: `기타`, `true`

따라서 카테고리가 `기타`라고 해서 항상 `false`인 것은 아닙니다.

## 처리 흐름

1. Controller가 HTTP 요청 본문을 받습니다.
2. Zod로 입력을 검증합니다.
3. Service가 분석 함수를 호출합니다.
4. 선택한 버전의 프롬프트를 생성해 Gemini API에 전달합니다.
5. 응답 텍스트를 JSON으로 변환합니다.
6. Zod로 분석 결과 구조를 검증합니다.
7. 검증된 객체를 HTTP 응답으로 반환합니다.

TypeScript 타입 검사는 개발 중 코드의 사용 방식을 확인합니다.
외부에서 받은 실제 데이터는 실행 중 Zod로 별도 검증합니다.

## API 사용 예시

### 상태 확인

```http
GET /health
```

응답:

```json
{
  "status": "ok"
}
```

이 응답은 서버가 요청에 응답하는지 확인합니다.
Gemini API 연결 상태를 검사하는 것은 아닙니다.

### 문의 분석

```http
POST /analyze
Content-Type: application/json
```

요청:

```json
{
  "text": "내일 예약을 취소해주세요."
}
```

응답 예시:

```json
{
  "category": "예약 취소",
  "summary": "내일 예정된 예약의 취소를 요청함.",
  "requiresAction": true
}
```

요약 문구는 실행마다 달라질 수 있습니다.

### PowerShell 요청 예시

서버를 켜둔 상태에서 별도 터미널로 실행합니다.

```powershell
$body = @{ text = "내일 예약을 취소해주세요." } | ConvertTo-Json

Invoke-RestMethod -Uri "http://127.0.0.1:3000/analyze" -Method Post -ContentType "application/json; charset=utf-8" -Body ([System.Text.Encoding]::UTF8.GetBytes($body))
```

### 잘못된 입력

공백만 있는 문자열, 누락된 `text`, 문자열이 아닌 값, 길이 제한을 벗어난 값은 입력 스키마에서 거부합니다.

공백 입력의 응답 예시:

```json
{
  "message": "text는 1~2000자의 문자열이어야 합니다.",
  "issues": []
}
```

HTTP 상태 코드는 `400`이며, 실제 `issues`에는 검증 실패 상세 정보가 포함됩니다.
입력 검증에 실패하면 분석 Service를 호출하지 않습니다.

## 출력 검증과 오류 처리

LLM 응답은 다음 순서로 검사합니다.

1. 응답 텍스트가 비어 있는지 확인
2. `JSON.parse`로 JSON 문자열 변환
3. Zod로 분석 결과 스키마 검사

검사 대상:

- `category`: 허용된 네 문자열 중 하나
- `summary`: 앞뒤 공백 제거 후 비어 있지 않은 문자열
- `requiresAction`: 불리언
- 필수 필드 존재 여부

현재는 프롬프트로 JSON 출력을 요청하고 반환값을 검증합니다.
모델 측 JSON Schema 기반 구조화 출력 기능은 적용하지 않았습니다.

### 시간 제한과 재시도

- 요청 1회 시간 제한: 60초
- SDK 내부 시도 횟수: 1회로 설정
- 애플리케이션 재시도 대상: HTTP 503
- 재시도 전 대기: 2초
- 최대 시도 횟수: 최초 호출 포함 2회
- 시간 초과·기타 오류·JSON 변환·스키마 오류는 자동 재시도하지 않음

시간 제한은 요청 1회에 적용됩니다.
503 재시도와 대기시간이 포함되면 분석 전체 시간은 60초를 넘을 수 있습니다.

외부 API 오류·시간 초과·응답 검증 오류를 구분한 HTTP 응답 처리는 추가 보강이 필요합니다.

## 안정성 검사

| 상황 | 확인 결과 |
|---|---|
| 공백만 있는 입력 | HTTP 400으로 거부 |
| 임시 1ms 시간 제한 | 요청 취소 오류 확인 후 60초로 복구 |
| 가짜 503 후 성공 | 총 2회 시도 후 성공 |
| 가짜 503 지속 | 총 2회 시도 후 실패 전달 |
| 가짜 400 | 재시도 없이 1회 종료 |

재시도 검사는 실제 API를 호출하지 않습니다.

```powershell
npx tsx src/retry-check.ts
```

이 검사는 재시도 함수의 동작을 확인하며, 외부 서비스가 실제로 복구되는 것을 보장하지는 않습니다.

## 고정 평가셋

직접 작성한 가상 문의 20개를 사용했습니다.
카테고리별 5개이며, 다음 유형을 포함합니다.

- 단순 예약 변경·취소
- 운영·위치 관련 정보 문의
- 인사·확인·업무 외 요청
- 정보 질문과 예약 처리 요청이 섞인 복합 문의
- 취소·변경 절차만 질문하고 실제 처리는 요청하지 않는 문장
- 담당자 확인·연락이 필요한 불만

### 평가 실행

```powershell
npx tsx --env-file=.env src/evaluate.ts
```

- 평가 문장을 순차적으로 호출합니다.
- 각 사례 종료 후 다음 사례까지 5초 대기합니다.
- 사례 하나가 실패해도 나머지 평가는 계속합니다.
- 실행 종료 시 `results/`에 시각이 포함된 JSON 파일을 생성합니다.
- 기존 결과 파일은 덮어쓰지 않습니다.
- 현재는 마지막에 일괄 저장하므로 실행을 강제 종료하면 해당 실행 결과가 저장되지 않습니다.

### 자동 평가 항목

- 분석 성공·실패 건수
- 분류 정답 여부
- 후속 조치 여부 정답
- 분석 함수 전체 소요시간
- 실패 오류

분석 성공은 응답 수신·JSON 변환·스키마 검증까지 통과했다는 뜻입니다.
실패 건은 정답 여부를 `null`로 저장합니다.

소요시간은 네트워크·모델 응답 대기·파싱·검증을 포함합니다.
재시도가 발생하면 재시도와 대기시간도 포함하며, 평가 사례 사이의 5초 대기는 제외합니다.
HTTP 서버를 거치지 않고 분석 함수를 직접 호출한 측정입니다.

## 프롬프트 A/B/C 비교

### 변경 내용

| 버전 | 프롬프트 구성 |
|---|---|
| A | 분류 기준·JSON 출력 조건을 지정한 기본 프롬프트 |
| B | A에 원문에 없는 의도·사실 추가와 발화 유형 변경을 금지하는 지시 추가 |
| C | B에 대상·장소·원인·목적의 추측을 제한하고 명시 정보·발화 유형을 보존하는 규칙 추가 |

C에는 평가 문장이나 개별 대조 예시를 넣지 않았습니다.

사용할 버전은 `src/analysis.config.ts`의 `promptVersion`으로 선택합니다.
동일한 평가 데이터와 모델·시간 제한·재시도 조건에서 버전별 한 번씩 실행했습니다.

### 정량 결과

| 지표 | A | B | C |
|---|---:|---:|---:|
| 분석 성공 | 20/20 | 20/20 | 20/20 |
| 분류 정답 | 20/20 | 20/20 | 20/20 |
| 후속 조치 여부 정답 | 20/20 | 20/20 | 20/20 |
| 평균 소요시간 | 12.95초 | 16.44초 | 22.39초 |
| 중앙 소요시간 | 14.70초 | 16.09초 | 21.24초 |
| 최대 소요시간 | 19.50초 | 27.04초 | 41.76초 |

세 버전에서 분류·후속 조치 판단의 차이는 관찰되지 않았습니다.

### 요약 표현 비교

| 입력 | A/B에서 관찰한 표현 | C에서 관찰한 표현 |
|---|---|---|
| 도착하기 위한 길을 알려주세요 | 매장·시설이라는 장소 맥락 추가 | 장소 종류를 특정하지 않고 길 안내 요청으로 요약 |
| 오늘 날씨가 참 좋네요. | 안부 인사로 해석 | 원문의 날씨 진술 유지 |

안부 인사라는 해석이 모든 서비스에서 오답인 것은 아닙니다.
이번 후속 실험에서는 원문에 명시되지 않은 대화 목적과 장소 성격을 덜 추가하는 방향을 목표로 삼았습니다.

B의 일반적인 금지 지시에서는 위 두 사례의 변화가 뚜렷하지 않았습니다.
C의 구체적인 제약을 추가한 실행에서는 원문 중심 표현이 관찰됐습니다.

### C에서 발견한 한계

- `change-04`: `다음 주로`를 `다음 주유로`라고 생성한 오타
- `other-05`: 번역 대상 문장을 생략하고 `아래 문장`이라고 표현해 요약 단독으로는 대상이 불명확함
- 일부 짧은 문장은 원문을 거의 그대로 반환해 압축 효과가 작음

스키마 검증은 구조를 검사하므로 오타·의미 변화·누락을 모두 검출하지 못합니다.

### 실험 해석

구체적인 요약 제약을 추가한 C 실행에서 일부 목표 사례의 표현이 달라졌습니다.
동시에 새로운 텍스트 오류도 관찰돼 C가 전체적으로 우수하다고 결론 내리지는 않았습니다.

실험의 한계는 다음과 같습니다.
