# LLM API MiniProject

사용자의 문의를 분류하고 요약하며, 직원의 후속 조치가 필요한지 판단하는 LLM 기반 API입니다.

Google Gemini API와 NestJS를 연결하고, 모델 응답 검증, 오류 대응, 고정 평가 데이터 기반 프롬프트 비교, Linux 및 Docker 실행까지 구현했습니다.

> 이 프로젝트는 모델을 직접 학습하는 프로젝트가 아니라, 외부 LLM API를 애플리케이션에 연결하고 결과를 검증·평가하는 프로젝트입니다.

## 주요 기능

- 문의를 예약 변경·예약 취소·이용 문의·기타로 분류
- 문의 내용을 한국어로 요약
- 직원의 후속 조치 필요 여부 판단
- Zod를 통한 요청 및 모델 응답 검증
- 외부 API 요청 타임아웃 설정
- HTTP 503 발생 시 제한적 재시도
- 고정 평가 데이터 20건을 이용한 프롬프트 A/B/C 비교
- 평가 입력·정답·모델 응답·처리시간·오류를 JSON으로 저장
- WSL 2 Ubuntu 및 Docker 컨테이너 실행 확인

실제 예약을 변경하거나 취소하지는 않습니다. 문의를 분석한 결과를 반환합니다.

## 분석 결과

```json
{
  "category": "예약 취소",
  "summary": "내일 예약을 취소해 주세요.",
  "requiresAction": true
}
```

| 필드 | 타입 | 의미 |
|---|---|---|
| `category` | 지정된 문자열 중 하나 | 문의 분류 |
| `summary` | 비어 있지 않은 문자열 | 문의 요약 |
| `requiresAction` | boolean | 직원의 처리 또는 추가 확인 필요 여부 |

### 분류 기준

| 카테고리 | 기준 |
|---|---|
| 예약 변경 | 기존 예약의 날짜나 시간 변경 요청 |
| 예약 취소 | 기존 예약 취소 요청 |
| 이용 문의 | 운영 시간, 위치, 이용 방법 등 정보 질문 |
| 기타 | 위 분류에 해당하지 않거나 의도가 불명확한 내용 |

`requiresAction`은 카테고리와 별도로 판단합니다.

예를 들어 정식 불만 접수와 담당자 연락 요청은 `기타`이면서 `requiresAction: true`일 수 있습니다.

예약 취소 절차만 묻고 실제 취소는 요청하지 않은 경우에는 `이용 문의`, `requiresAction: false`로 판단하도록 설계했습니다.

## 처리 흐름

1. 클라이언트가 문의 문장을 전송합니다.
2. 컨트롤러에서 요청 본문을 검증합니다.
3. 서비스가 공통 분석 함수를 호출합니다.
4. 선택한 버전의 프롬프트와 문의를 Gemini에 전달합니다.
5. 모델 응답 문자열을 JSON으로 파싱합니다.
6. Zod 스키마로 결과를 검증합니다.
7. 검증된 분석 결과를 반환합니다.

모델 응답은 바로 신뢰하지 않고 다음 순서로 처리합니다.

```text
응답 문자열 → JSON 파싱 → unknown 값 → Zod 검증 → AnalysisResult
```

TypeScript 타입은 개발 시 코드의 타입을 검사하고, Zod는 실행 중 외부에서 받은 실제 데이터의 구조를 검사합니다.

## API 사용법

### GET /health

서버 응답 상태를 확인합니다. Gemini API 연결 성공 여부까지 검사하는 엔드포인트는 아닙니다.

```bash
curl -i http://127.0.0.1:3000/health
```

응답:

```json
{
  "status": "ok"
}
```

### POST /analyze

요청 본문:

```json
{
  "text": "내일 예약을 취소해주세요."
}
```

Ubuntu에서 요청:

```bash
curl -i http://127.0.0.1:3000/analyze \
  -H "Content-Type: application/json" \
  -d '{"text":"내일 예약을 취소해주세요."}'
```

Windows PowerShell에서 요청:

```powershell
$body = @{ text = "내일 예약을 취소해주세요." } | ConvertTo-Json

Invoke-RestMethod `
  -Uri "http://127.0.0.1:3000/analyze" `
  -Method Post `
  -ContentType "application/json; charset=utf-8" `
  -Body ([System.Text.Encoding]::UTF8.GetBytes($body))
```

정상 응답 예시:

```json
{
  "category": "예약 취소",
  "summary": "내일 예약을 취소해 주세요.",
  "requiresAction": true
}
```

요약 문구는 모델 실행에 따라 달라질 수 있습니다.

### 입력 검증

`text`는 앞뒤 공백 제거 후 1~2000자인 문자열이어야 합니다.

공백 입력 확인:

```bash
curl -i http://127.0.0.1:3000/analyze \
  -H "Content-Type: application/json" \
  -d '{"text":"   "}'
```

HTTP 400과 다음 메시지를 반환합니다. 응답에는 상세 검증 정보인 `issues`도 포함됩니다.

```text
text는 1~2000자의 문자열이어야 합니다.
```

입력 검증에서 실패한 요청은 Gemini 호출 전에 차단합니다.

## 모델 응답 검증 및 오류 대응

### 응답 검증

- 응답이 비어 있는지 확인
- `JSON.parse`로 JSON 파싱
- `AnalysisSchema.safeParse`로 필드와 타입 검증
- 검증에 성공한 데이터만 반환

프롬프트로 JSON 출력을 요청하고 애플리케이션에서 결과를 검증하는 방식입니다. 제공자 측 JSON 스키마 기반 구조화 출력은 적용하지 않았습니다.

스키마 검증 통과는 데이터 형식이 맞다는 의미이며, 요약의 사실성이나 분류의 정확성까지 보장하지는 않습니다.

### 타임아웃과 재시도

| 설정 | 값 |
|---|---|
| 요청별 타임아웃 | 60초 |
| 애플리케이션 최대 시도 횟수 | 2회 |
| 재시도 간 대기 | 2초 |
| 재시도 대상 | HTTP 503 |
| SDK 요청 시도 설정 | `attempts: 1` |

HTTP 503은 일시적인 모델 수요 증가 등으로 발생할 수 있어 한 번 재시도합니다.

HTTP 400, 타임아웃, JSON 파싱 실패, 스키마 검증 실패는 애플리케이션 재시도 대상에 포함하지 않았습니다.

60초는 개별 요청에 대한 제한입니다. 재시도가 발생하면 전체 처리시간은 60초를 초과할 수 있습니다.

외부 API 오류를 종류별 HTTP 상태 코드로 변환하는 처리는 향후 개선 항목입니다.

### 재시도 로직 확인

```bash
npx tsx src/retry-check.ts
```

실제 API를 호출하지 않는 모의 요청으로 다음을 확인했습니다.

- 첫 요청에서 503 발생 후 두 번째 요청 성공
- 연속 503 발생 시 최대 두 번 시도 후 실패
- 400 오류 발생 시 재시도하지 않고 실패

## 고정 데이터 평가

카테고리별 5건씩 총 20건의 평가 데이터를 구성했습니다.

- 예약 변경: 5건
- 예약 취소: 5건
- 이용 문의: 5건
- 기타: 5건

단순 요청 외에도 다음 조건을 포함했습니다.

- 정보 질문과 예약 처리 요청이 함께 있는 문의
- 변경·취소 관련 단어가 있지만 실제 처리를 요청하지 않은 문의
- 담당자의 확인과 연락을 요청하는 불만
- 인사, 확인 응답, 일상적인 진술
- 서비스 범위 밖의 요청

### 평가 실행

```bash
npx tsx --env-file=.env src/evaluate.ts
```

평가는 HTTP 서버를 거치지 않고 공통 분석 함수를 직접 호출합니다.

사례를 순차 처리하고, 각 사례 처리 후 5초 대기합니다. 한 사례가 실패해도 오류를 기록하고 다음 사례를 진행합니다.

결과는 다음 형태의 파일로 저장합니다.

```text
results/evaluation-실행시각.json
```

파일명의 시각은 UTC 기준입니다.

현재 구현은 전체 평가가 끝난 뒤 결과를 저장합니다. 실행을 중간에 종료하면 해당 실행의 결과 파일이 저장되지 않을 수 있습니다.

### 기록 항목

- 평가 사례 ID
- 입력 문장
- 기대 카테고리
- 기대 후속 조치 여부
- 실제 모델 응답
- 호출·파싱·검증 성공 여부
- 카테고리 일치 여부
- 후속 조치 여부 일치 여부
- 처리시간
- 오류 메시지
- 실행에 사용한 분석 설정

`success`는 호출과 결과 검증이 완료되었다는 의미입니다. 정답 일치 여부는 `categoryCorrect`, `actionCorrect`로 별도 기록합니다.

처리시간에는 모델 호출과 응답 처리, 발생한 재시도 대기가 포함됩니다. 사례 사이의 5초 대기는 제외합니다.

## 프롬프트 A/B/C 실험

카테고리와 출력 필드는 유지하고 요약 제약을 변경했습니다.

| 버전 | 변경 내용 |
|---|---|
| A | 기본 분류·요약·후속 조치 판단 규칙 |
| B | 원문에 없는 의도·사실 추가 금지, 진술을 질문·요청으로 바꾸지 않도록 제약 |
| C | B의 제약에 더해 대상·장소·원인·목적 추측 금지, 일반적인 표현 및 발화 유형 유지 |

C에는 특정 평가 문장의 정답 예시를 넣지 않고 일반적인 요약 원칙을 추가했습니다.

실행 버전은 `src/analysis.config.ts`의 `promptVersion`으로 선택합니다.

### 실험 결과

동일한 고정 데이터 20건에 대해 버전별로 한 번씩 실행했습니다.

| 항목 | A | B | C |
|---|---:|---:|---:|
| 처리 성공 | 20/20 | 20/20 | 20/20 |
| 카테고리 일치 | 20/20 | 20/20 | 20/20 |
| 후속 조치 여부 일치 | 20/20 | 20/20 | 20/20 |
| 평균 처리시간 | 12.95초 | 16.44초 | 22.39초 |
| 중앙 처리시간 | 14.70초 | 16.09초 | 21.24초 |
| 최대 처리시간 | 19.50초 | 27.04초 | 41.76초 |

### 요약 표현 비교

입력:

```text
도착하기 위한 길을 알려주세요
```

| 버전 | 요약 |
|---|---|
| A | 매장 위치나 찾아오는 길에 대한 문의입니다. |
| B | 매장이나 시설에 찾아오는 길을 묻는 문의입니다. |
| C | 도착하기 위한 길을 알려달라고 문의함. |

C에서는 원문에 명시되지 않은 매장·시설이라는 대상을 추가하지 않았습니다.

입력:

```text
오늘 날씨가 참 좋네요.
```

| 버전 | 요약 |
|---|---|
| A | 날씨에 대한 일상적인 안부 인사를 건네는 내용입니다. |
| B | 날씨에 대한 일상적인 안부 인사를 건네는 내용입니다. |
| C | 오늘 날씨가 참 좋네요. |

안부 인사라는 해석이 일반적인 대화에서 반드시 잘못된 것은 아닙니다. 이 프로젝트에서는 원문에 명시된 내용과 발화 유형을 유지하는 방향을 비교했습니다.

### 해석과 한계

- 카테고리와 후속 조치 여부는 A/B/C 모두 일치하여 해당 지표의 개선은 관찰되지 않았습니다.
- C에서는 일부 사례에서 원문에 없는 대상이나 대화 의도를 추가하는 표현이 줄었습니다.
- C에서도 오탈자와 요약 대상 생략이 관찰되어 전체 요약 품질이 우수하다고 단정할 수 없습니다.
- 요약 품질은 사례별로 검토했으며 전체 데이터에 대한 별도 정량 점수는 산출하지 않았습니다.
- 20건의 소규모 데이터에 버전별 한 번씩 실행한 결과입니다.
- 기존 평가 결과를 참고하여 프롬프트를 수정했으므로 독립된 최종 시험 데이터로 볼 수 없습니다.
- 외부 API의 부하와 응답 변동이 있어 처리시간 차이를 프롬프트만의 영향으로 단정할 수 없습니다.
- 더 많은 독립 평가 데이터와 반복 실행이 필요합니다.

## 평가 결과 파일

기존 기록은 보존하고, 파일 내부의 기록 형식 버전과 분석 설정을 기준으로 구분했습니다.

| 구분 | 결과 파일 |
|---|---|
| 초기 평가 | [evaluation-2026-11-03T15-09-12-676Z.json](results/evaluation-2026-11-03T15-09-12-676Z.json) |
| 상세 기록 추가 | [evaluation-2026-11-03T15-30-55-613Z.json](results/evaluation-2026-11-03T15-30-55-613Z.json) |
| 프롬프트 A | [evaluation-2026-11-04T14-43-32-494Z.json](results/evaluation-2026-11-04T14-43-32-494Z.json) |

| 프롬프트 C | [evaluation-2026-11-04T16-26-14-305Z.json](results/evaluation-2026-11-04T16-26-14-305Z.json) |

### 기록 형식 변경

| 형식 | 기록 내용 |
|---|---|
| 초기 형식 | ID, 처리 성공 여부, 정답 비교, 처리시간, 오류 |
| 버전 2 | 입력 문장, 기대 결과, 실제 모델 응답 추가 |
| 버전 3 | 실행에 사용한 모델·프롬프트 버전·타임아웃·재시도 설정 추가 |

초기 평가에서는 20건 중 1건이 HTTP 503으로 실패했습니다. 오류 메시지는 모델 수요 증가에 따른 일시적 사용 불가였으며, 문의에 주차장 정보가 없어서 실패한 것으로 해석하지 않았습니다.

초기 실행과 이후 실행은 기록 및 실행 조건이 달라 프롬프트 A/B/C의 직접 비교 자료와 구분했습니다.

## Linux 실행 확인

Windows에서 개발한 프로젝트를 WSL 2 Ubuntu에 별도로 내려받아 실행했습니다.

- Ubuntu 홈 폴더에 저장소 복제
- nvm으로 Ubuntu용 Node.js 설치
- `npm ci`로 Linux 환경의 패키지 설치
- 타입 검사 및 빌드 통과
- `/health` 응답 확인
- 실제 Gemini 문의 분석 응답 확인
- 공백 입력 검증 확인

Windows의 `node_modules`를 복사하지 않고 Ubuntu에서 패키지를 새로 설치했습니다.

VS Code의 WSL 연결을 사용하여 Ubuntu 쪽 파일을 편집하고 실행했습니다.

## Docker 실행

### 이미지 빌드

Docker가 실행 중인 환경에서 프로젝트 최상위 폴더를 기준으로 실행합니다.

```bash
docker build -t llm-api-miniproject:local .
```

Dockerfile은 두 단계로 구성했습니다.

| 단계 | 작업 |
|---|---|
| 빌드 | 패키지 설치, TypeScript 빌드, 개발 전용 패키지 제거 |
| 실행 | 빌드 결과와 실행용 패키지 복사, 일반 사용자로 서버 실행 |

기반 이미지는 `node:26.13.0-bookworm-slim`입니다.

`.dockerignore`로 API 키가 담긴 `.env`, 로컬 패키지, 기존 빌드 결과, Git 이력, 평가 결과 등을 빌드 대상에서 제외합니다.

### 컨테이너 실행

프로젝트 최상위 폴더에 실제 API 키가 담긴 `.env`를 준비합니다.

기존 서버가 3000번 포트를 사용하고 있다면 먼저 종료합니다.

```bash
docker run -d \
  --name llm-api-mini \
  --env-file .env \
  -p 127.0.0.1:3000:3000 \
  llm-api-miniproject:local
```

| 옵션 | 역할 |
|---|---|
| `-d` | 백그라운드 실행 |
| `--name` | 컨테이너 이름 지정 |
| `--env-file` | 환경변수 전달 |
| `-p` | 호스트와 컨테이너 포트 연결 |

API 키는 이미지에 포함하지 않고 실행할 때 전달합니다.

이 명령어는 호스트의 `127.0.0.1:3000`에만 포트를 공개합니다.

### 상태와 로그 확인

```bash
docker ps
docker logs llm-api-mini
```

실시간 로그 확인:

```bash
docker logs -f llm-api-mini
```

`Ctrl + C`로 실시간 로그 보기만 종료할 수 있으며, 백그라운드 컨테이너는 계속 실행됩니다.

### 동작 확인

```bash
curl -i http://127.0.0.1:3000/health
```

```bash
curl -i http://127.0.0.1:3000/analyze \
  -H "Content-Type: application/json" \
  -d '{"text":"내일 예약을 취소해주세요."}'
```

```bash
curl -i http://127.0.0.1:3000/analyze \
  -H "Content-Type: application/json" \
  -d '{"text":"   "}'
```

컨테이너 환경에서 다음을 확인했습니다.

| 확인 항목 | 결과 |
|---|---|
| 컨테이너 실행 | `Up` 상태 |
| NestJS 시작 | 정상 시작 로그 |
| `GET /health` | HTTP 200 |
| 정상 문의 분석 | HTTP 200 및 예약 취소 분석 결과 |
| 공백 입력 | HTTP 400 및 검증 오류 |

### 중지 및 재시작

```bash
docker stop llm-api-mini
docker start llm-api-mini
```

기존 컨테이너는 생성 당시의 이미지, 환경변수, 포트 설정을 사용합니다.

### 코드 변경 반영

외부 소스코드 수정은 이미 만들어진 이미지와 컨테이너에 자동 반영되지 않습니다.

수정한 코드로 이미지를 다시 빌드하고 컨테이너를 교체합니다.

```bash
docker build -t llm-api-miniproject:local .
docker stop llm-api-mini
docker rm llm-api-mini
docker run -d \
  --name llm-api-mini \
  --env-file .env \
  -p 127.0.0.1:3000:3000 \
  llm-api-miniproject:local
```

`.env` 값만 변경한 경우 이미지 재빌드는 필요하지 않지만, 새 값을 전달하여 컨테이너를 다시 생성해야 합니다.

## 배운 점

- TypeScript 타입 검사와 실행 중 데이터 검증의 역할이 다름을 확인했습니다.
- 외부 LLM 응답을 파싱·검증하여 애플리케이션에서 사용할 수 있는 데이터로 변환했습니다.
- 고정 평가 데이터와 실행 설정을 함께 기록하여 실험 결과를 추적했습니다.
- 분류 정확도가 같아도 요약 표현과 원문 충실도는 달라질 수 있음을 관찰했습니다.
- API 실패를 분류 오답과 구분하고 제한적 재시도를 적용했습니다.
- Windows와 Linux의 개발 도구 및 파일 공간을 구분하여 실행했습니다.
- Docker 이미지와 컨테이너의 차이, 환경변수 전달, 포트 연결, 로그 확인을 실습했습니다.

## 한계 및 향후 개선

- 평가 데이터 확대 및 프롬프트 수정에 사용하지 않은 독립 평가 데이터 구성
- 같은 조건의 반복 실행을 통한 변동성 확인
- 요약 충실도·정보 누락·발화 유형 보존에 대한 평가 기준 수립
- 외부 API 오류 종류별 HTTP 응답 처리
- 실제 시도 횟수와 토큰 사용량 기록
- 제공자 측 구조화 출력 적용 검토
- 요청 제한 및 인증 등 외부 공개 운영을 위한 기능 추가
- 평가 실행 도중에도 결과를 보존하도록 저장 방식 개선

현재는 로컬 실행과 기능 검증을 위한 미니프로젝트이며, 공개 서비스 운영까지 구현한 상태는 아닙니다.
